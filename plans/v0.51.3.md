# v0.51.3 plan: bounded metadata

## Scope

Give high-cardinality catalog operations an explicit ordering, streaming, and
failure contract. Do not require a pre-count before the first result.

## Outcomes

- Bounded data-file APIs have one documented ordering contract.
- File-column statistics and delete-file metadata stream or page without a
  global prefix scan followed by per-row lookups.
- Snapshot history, partition metadata, mapping metadata, export, verification,
  and diagnostics have a documented boundedness class.
- Interactive operations support cancellation and obey admission limits.
- Administrative online operations stream progress and remain memory-bounded.
- Offline or rebuild operations may scan the catalog, but report cost, remain
  memory-bounded, and restart where practical.
- Response limits distinguish in-flight memory from an optional total-result
  policy. A low undocumented result ceiling does not remain in the default
  path.
- A stream that encounters an object-store failure returns an error instead of a
  truncated success.
- Cancellation releases admission permits and catalog handles.

## Implementation choices

Choose one data-file order and use it in the page, stream, legacy, simple-query,
extended-query, and `COPY` paths. Keep the choice in the public API contract.

Use one scan contract that carries the operation kind and snapshot ID. Carry a
known row count or an optional estimate when available. An estimate must never
turn an incremental operation into a full pre-count.

Treat verification as a complete streaming operation. Do not apply an
interactive result limit to a command whose job is to check the full catalog.

## Black-box checks

| Scenario | Setup | Expected result |
|---|---|---|
| Non-monotonic file order | Create files with deliberately non-monotonic `file_order` values. | Stream, pages, legacy list, simple query, extended query, and `COPY` return the same documented order. |
| Large metadata result | Create a valid result larger than 16 MiB. | The result streams without exceeding the in-flight memory budget. |
| Slow consumer | Read one row at a time with a delayed client. | Memory stays within the configured budget and the server does not queue unbounded rows. |
| Early disconnect | Disconnect after the first row. | The scan, permit, and catalog handle are released. |
| Mid-stream store failure | Inject an object-store error after several rows. | The client receives an error and not a successful truncated result. |
| Admission cancellation | Cancel while a high-cardinality operation waits for a permit. | The wait ends and the permit is available for another operation. |
| Full verification | Run verification on a catalog larger than the interactive limit. | Verification scans the full catalog, streams progress, and reports failures. |

## Exit conditions

Document every remaining materializing API with its explicit bound or bounded
alternative. Run parity, cancellation, disconnect, fault-injection, and memory
tests across the relevant Rust and PG-wire paths.
